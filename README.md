# Крот · Krot

Android 8+ (minSdk 26) SOCKS5-прокси поверх аутентифицированного DNS-туннеля.
Сервер — один Python-файл. Без root и без VpnService: слот VPN не занимает.

**v0.1.3 — экспериментальная первая версия.** TCP CONNECT через SOCKS5; UDP ASSOCIATE,
системная маршрутизация всех приложений и голосовые/видеозвонки по UDP отсутствуют.
Telegram и другие приложения подключаются своим SOCKS5. Работает только если
доступный рекурсивный DNS действительно ходит к вашей делегированной зоне.
Реальная скорость/совместимость с оператором пока не измерены. 1 Мбит/с не гарантируется.

## 1. Домен и сервер

Пример: сервер с публичным IPv4 `203.0.113.10` (замените на реальный адрес), ваш
домен `example.ru`. В **родительской DNS-зоне** создайте:

| Имя | Тип | Значение |
|---|---|---|
| `ns-krot.example.ru` | A | IPv4 сервера |
| `tunnel.example.ru` | NS | `ns-krot.example.ru.` |

Не включайте HTTP/CDN-проксирование для `ns-krot`. NS должен быть A/AAAA, не CNAME.
Делегируется именно подзона `tunnel`, не основной домен. Сервер использует UDP/53;
не меняйте существующий DNS основного домена. Если IP сервера сам в whitelist,
обычный прямой транспорт может оказаться намного быстрее DNS-туннеля.

Быстрая установка как systemd-сервис (Debian 12+ / Ubuntu 24.04+, от root): скрипт
ставит зависимости, генерирует пароль в `/etc/krot.env`, открывает 53/udp в ufw/firewalld
и проверяет делегирование. Повторный запуск обновляет код и сохраняет пароль.

```bash
git clone https://github.com/DarkPrince922/Krot.git /opt/krot
sudo bash /opt/krot/server/install.sh tunnel.example.ru
```

Вручную, Ubuntu 22.04+ / Debian 12+:

```bash
git clone https://github.com/DarkPrince922/Krot.git
cd Krot
python3 --version   # требуется Python >=3.11; на Ubuntu 22.04 установите отдельно
python3 -m venv .venv
.venv/bin/pip install -r server/requirements.txt
# Нужен отдельный IP или свободный UDP/53, не работающий на нём named/dnsmasq.
sudo ss -lunp 'sport = :53'
```

Не выключайте `systemd-resolved` автоматически: его stub на 127.0.0.53 может
сосуществовать с привязкой к публичному/локальному адресу интерфейса. Узнайте
IP интерфейса через `ip -brief address`; при NAT это часто частный IP VPS.

```bash
# Случайный пароль — сохраните и введите в приложение.
read -rsp 'KROT_PASSWORD: ' KROT_PASSWORD; echo
export KROT_PASSWORD
sudo --preserve-env=KROT_PASSWORD .venv/bin/python server/krot.py \
  --domain tunnel.example.ru --bind YOUR_INTERFACE_IP --port 53
```

Откройте UDP/53 в firewall VPS и у хостера. Сервер не рекурсор: `dig example.org
@SERVER_IP` специально не получает ответа. Проверять туннель нужно клиентом,
а не ожиданием TXT от пустого `tunnel.example.ru`. Обычный `dig +trace
x.tunnel.example.ru` покажет делегацию, но финальный запрос без шифра останется
без ответа. Сервер не отвечает на apex SOA/NS — некоторые резолверы могут требовать
их; compatibility проверяется на вашей сети. Запросы через оператора видны как
DNS-трафик; название и молчание на чужие запросы не гарантируют «антидетект».

Для постоянной работы используйте [пример systemd](server/krot.service).
Пути в нём предполагают установку в `/opt/krot` и venv `/opt/krot/.venv`.
Пароль положите в `/etc/krot.env` с правами 0600:

```ini
KROT_PASSWORD=YOUR_LONG_RANDOM_PASSWORD
```

Сервис работает от DynamicUser, получает только capability bind UDP/53, имеет
ограничения ресурсов и не требует root для исходящих TCP. Приватные/loopback/
link-local адреса назначения запрещены по умолчанию; `--allow-private` нужен
только для осознанного использования сервера как шлюза в свою LAN.

## 2. Android

Готовый debug APK собирается в **GitHub → Actions → Test and build Krot →
Artifacts → Krot-debug-APK**. Это тестовая сборка. Для постоянных обновлений
подписывайте release своим постоянным ключом; ключи и пароль в репозитории не хранятся.

1. Установите APK; откройте **Настройки**.
2. Зона: `tunnel.example.ru`. Пароль — тот же, что `KROT_PASSWORD`.
3. Nameserver оставьте пустым: берётся системный DNS через ConnectivityManager.
   IPv4 DNS оператора имеют приоритет. IPv6 пробуется после IPv4, начальная
   проверка IPv6 ограничена двумя попытками; вручную заданный IPv6 поддерживается.
   При необходимости укажите IP резолвера оператора вручную. Зарубежный DNS не
   добавляется автоматически. Private DNS/DoT может не работать при блокировках;
   приложение отправляет обычные UDP DNS-запросы напрямую на выбранный резолвер.
4. TXT, конвейер 12, максимум ответа 900; сервер уменьшает фактический размер
   по UDP-бюджету. При проблемах попробуйте 600 или 300, затем глубину 8.
   Для скорости поднимайте конвейер 16 → 24 → 32, пока ↓ кБ/с растёт, а RTT не
   уходит вверх (резолвер оператора начал ограничивать запросы).
5. Нажмите **Запустить**, разрешите уведомления. Для длительной работы на
   прошивках с агрессивной экономией батареи разрешите фоновую работу вручную.
6. Telegram → Настройки → Данные и память → Прокси → SOCKS5:
   сервер `127.0.0.1`, порт `1080`, username/password пустые.

При смене сети клиент обновляет системные DNS и привязывает сокеты к актуальной
Android Network; старые TCP-потоки закрываются. Автозапуск после перезагрузки не
включён. Обычный foreground-сервис переживает сворачивание, но принудительное
закрытие приложения и политики прошивки могут остановить его.

Режим LAN слушает `0.0.0.0`, **без SOCKS-аутентификации**. Включайте только в
доверенной сети; на ноутбуке используйте IP телефона и настроенный порт. Android
hotspot/прошивка могут блокировать соединения клиентов к телефону.

## Сборка и тесты

Android Studio / JDK 17 / SDK 35. Gradle wrapper закреплён на 8.13:

```bash
python3 -m venv .venv
.venv/bin/pip install -r server/requirements.txt
.venv/bin/python -m unittest discover -s server -v
# Python для интеграционных JVM-тестов должен быть в PATH и иметь эти зависимости.
export PATH="$PWD/.venv/bin:$PATH"
cd android
./gradlew testDebugUnitTest lintDebug assembleDebug
# app/build/outputs/apk/debug/app-debug.apk
```

CI выполняет серверные тесты и Android JVM-тесты, включая настоящий путь
Kotlin SOCKS → UDP DNS → Python → TCP echo для TXT/NULL/A. Проверяется большой
бинарный поток, half-close, общие криптовекторы, DNS-лимиты и malformed-ответы.
Отдельные серверные тесты имитируют потери ответов, перестановку DATA и повторы.
Это loopback-тесты; они не заменяют испытание на устройстве через рекурсор
оператора. UI/Doze/смена сети на физическом Android ещё требуют такой проверки.
