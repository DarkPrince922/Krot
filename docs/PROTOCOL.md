# KrotP v1 · реализованная спецификация

ТЗ оставляло неопределёнными бинарный формат, ACK, направление nonce и порядок
ответов при конвейере. Эта спецификация определяет совместимый контракт клиента
и сервера этого репозитория. Совместимость с iodine и другими DNS-туннелями не предполагается.

## DNS

Настройка `domain` — **полная делегированная зона** `tunnel.example.ru`.
Имя: `<base32(ciphertext), метки до 63>.<base32(session[8] || nonce[12])>.<domain>`.
Base32 RFC 4648 без padding, регистр игнорируется. `nonce` — случайный префикс
4 байта на сессию и увеличивающийся uint64 BE, первый счётчик 1.
Каждый повтор операции получает новый nonce и новое имя. Максимум имени — 255
байт в wire format, а не 255 байт данных; реальный полезный upload обычно около
80–90 байт на запрос для короткого домена. Размер вычисляется клиентом.

UDP, IN, TXT (16), NULL (10) или A (1). RD=1. OPT/EDNS0 с UDP size 1232 обязателен.
Ответ AA=1, RA=0, TTL=0, OPT 1232. Несогласованный тип внутри сессии игнорируется.
TXT — **одна RR с несколькими character-string до 255 байт**, их нужно склеить
до base64url decode. Кодировка без padding. NULL — бинарный encrypted packet.
A — `uint16 BE packet_length || packet`, нарезанный по 3 байта; каждый RDATA
содержит `uint8 index || 3 bytes`, последняя часть дополнена нулями. RR надо
сортировать по index: резолвер может переставить их. A существенно менее эффективен
и экспериментален; не каждый рекурсор поддерживает NULL и необычные A.

Ответный packet: `nonce[12] || ciphertext || tag[16]`.
Предел 1232 относится ко всему DNS-пакету. Сервер подбирает размер downstream
чанка при OPEN, считая фактический размер сериализованного ответа с вопросом,
шифром и кодированием. Пользовательский размер 100–1100 — верхний предел;
900 байт TXT не обещаются при лимите UDP 1232. TC-пакеты клиент отвергает.
Для мобильной цепочки рекомендуются TXT и верхний предел 600–900.

Сервер не является recursive/open DNS resolver. Посторонние имена, отсутствие
EDNS0, невалидные кадры, неизвестные сессии без PING и неверный MAC игнорируются.
Он намеренно не отвечает на SOA/NS apex: делегация должна быть в родительской зоне.
**Некоторые резолверы требуют apex SOA/NS и могут не работать с таким silent-only
сервером**. Это ограничение v1 и его нужно проверить на конкретном операторе;
публичный DNS-туннель нельзя сделать гарантированно необнаруживаемым молчанием.

## Ключи

Все HKDF — SHA-256, 32 байта. `password` UTF-8; зона lowercase без trailing dot.

```
master  = HKDF(password, salt="krot-v1", info=domain)
sub     = HKDF(master, salt=session[8], info="")
up      = HKDF(sub, salt="krot-v1", info="up")
down    = HKDF(sub, salt="krot-v1", info="down")
```

ChaCha20-Poly1305 IETF (96-bit nonce), AEAD associated data `krot-v1-up` /
`krot-v1-down`. Bouncy Castle lightweight API и Python cryptography реализуют
тот же примитив; libsodium не требуется как конкретная библиотека. Два направления
используют разные ключи: совпадение nonce между направлениями безопасно. Сервер
генерирует собственный случайный префикс 4 байта и свой uint64 счётчик. Ключи не
передаются. Для пароля используйте случайные минимум 128 бит: HKDF не замедляет
перебор слабого пароля. TLS приложений проходит внутри TCP неизменным.

## Кадр

Все числа unsigned, big-endian; Android ограничивает счётчики 0..2^63−1.
Заголовок 23 байта:

| Поле | Размер |
|---|---:|
| type | 1 |
| stream_id | 4 |
| seq | 8 |
| ack | 8 |
| payload_length | 2 |
| payload | payload_length |

Лишние байты и неправильная длина запрещены. `stream_id=0` зарезервирован для
PING/PONG. Идентификаторы потоков положительные и не переиспользуются в сессии.
`seq` — **номер блока**, начиная с нуля, не смещение байта; длины блоков могут
различаться. `ack` в DATA/POLL/FIN/CLOSE клиента — номер следующего ожидаемого
блока downstream (cumulative ACK). Устаревший ACK игнорируется, ACK за пределами
уже созданных блоков отклоняется.

| type | Имя | Payload / поведение |
|---:|---|---|
| 1 | OPEN | host_length:u8, host:ASCII, port:u16, max_response:u16 |
| 2 | DATA | TCP bytes; ACK с тем же seq после принятия upstream |
| 3 | CLOSE | Клиент закрывает весь поток; от сервера — EOF, seq=число downstream блоков |
| 4 | POLL | Запрос именно downstream блока seq, ack=следующий недоставленный |
| 5 | PING | stream=0, без payload, создаёт сессию и проверяет доступность |
| 6 | PONG | Нет данных сейчас / ответ на PING |
| 7 | ACK | Ответ на OPEN: согласованный chunk_size:u16; остальные ACK без payload |
| 8 | ERROR | Соединение отказано, поток неизвестен или лимит/протокол нарушен |
| 9 | FIN | Half-close upstream, seq=общее число upstream блоков; downstream продолжает работать |
| 10 | OPEN_PART | Расширение v1 для длинного OPEN: seq=индекс части, ack=число частей (1–4) |

Если OPEN не помещается в одно имя: сначала OPEN_PART с частями OPEN payload,
каждый подтверждается ACK; затем OPEN с пустым payload коммитит сборку. Только
после полного OPEN открывается TCP. Повтор OPEN для одного stream идемпотентен,
проверяет host/port и ожидает то же подключение, не открывая второе.

## Надёжность и конвейер

Глобальный семафор ограничивает одновременно выполняющиеся DNS-RPC настройкой
8–16. В upload читаются ограниченные очереди Future; DATA может прийти не по
порядку. Сервер хранит окно 64 блоков, записывает в TCP только последовательные
блоки, повторы старых seq не записывает. ACK означает, что сервер принял блок в
ограниченный буфер, а не что удалённое приложение его прочитало.

Downstream сохраняется до cumulative ACK, поэтому потерянный DNS-ответ не теряет
TCP-данные. Несколько poll-lanes запрашивают разные seq; клиент переупорядочивает
их, выдаёт SOCKS-приложению подряд и только затем двигает ACK. Если requested
seq ещё нет, сервер возвращает PONG, lane повторяет тот же seq. При отсутствии TCP-трафика более 3s poll-lanes
снижают частоту до одного опроса за 1.5s на lane. EOF обрабатывается
только после всех блоков до CLOSE.seq. Upstream FIN отправляется после ACK всех
переданных блоков; полное CLOSE освобождает TCP.

Ретрай: новый DNS transaction ID и nonce; первая попытка
`timeout=max(300ms,1.5×EWMA RTT)`, для OPEN минимум 2500ms. Каждая следующая
попытка увеличивает этот timeout в 1.5 раза, максимум до 8000ms; всего 7 попыток.
RTT для backoff фиксируется на начало RPC: успешные параллельные POLL не сбивают
его рост. Временные UDP send/receive/bind ошибки также повторяются. Только
аутентифицированный ERROR терминален сразу. В авто-режиме сначала пробуются
системные IPv4 DNS, затем IPv6 (для начального IPv6 PING не более двух попыток).
Ручной IPv6 не ограничен этим исключением; после подключения все RPC получают
полные 7 попыток независимо от семейства адреса. Нет бесконечного удержания
безнадёжного TCP-потока. Heartbeat при работающем сервисе каждые 1.5s, статус
меняется при длительной недоступности. После рестарта сервера существующие TCP
потоки потребуется открыть заново; бесшовного восстановления TCP v1 не обещает.

Лимиты сервера: 128 сессий, 64 активных потока/сессию, 4096 идентификаторов
потоков за жизнь сессии, 64 блока в каждом направлении, 512 DNS-handler задач,
4096 повторов nonce в LRU. Сессии без аутентифицированных запросов удаляются
после 120s. Клиент принимает до 32 SOCKS-соединений. LAN off по умолчанию.
EOF/закрытые stream tombstones сохраняются до конца сессии, предотвращая повторное
открытие от запоздалого OPEN. При исчерпании stream IDs нужно перезапустить клиент.
